### 1. ✅ Idempotency Middleware & Integration

**What:** Prevents duplicate processing of critical operations

**Files Created:**
- `backend/src/common/middleware/idempotency.middleware.ts`

**Integration:**
- `PaymentsModule` → Applied to checkout endpoints
- `PaymentsService.handleStripeWebhook()` → Webhook deduplication

**How It Works:**
```typescript
// Frontend sends UUID on checkout
POST /payments/stripe/checkout-session
Headers: { 'Idempotency-Key': 'abc-123-def-456' }

// First request: Processes and caches result
→ Creates order, returns checkout URL

// Duplicate request (network retry, double-click):
→ Returns cached result (409 Conflict)
→ No duplicate charge, no duplicate order
```

**Webhook Deduplication:**
```typescript
// Stripe sends webhook with event.id = "evt_abc123"
// First delivery: Process and mark as processed
// Second delivery: Detect duplicate, return success (idempotent)

async handleStripeWebhook(event: Stripe.Event) {
  const idempotencyKey = `stripe_webhook:${event.id}`;
  
  if (await this.checkWebhookIdempotency(idempotencyKey)) {
    return { received: true }; // Duplicate, already processed
  }
  
  await this.markWebhookAsProcessing(idempotencyKey);
  // ... process webhook
  await this.markWebhookAsProcessed(idempotencyKey);
}
```

**Production Impact:**
- **Before:** Duplicate webhook → duplicate payment processing → customer charged twice
- **After:** Duplicate webhook → detected and ignored → customer charged once

**Interview Answer:**
> "We prevent duplicate payment processing using idempotency keys. The frontend generates a UUID and includes it in the Idempotency-Key header. We store the key + response in MongoDB with 24-hour TTL. If the same key arrives again (network retry, user double-click), we return the cached response with 409 Conflict. For Stripe webhooks, we use the Stripe event ID as the idempotency key. This is critical because Stripe retries webhooks for 3 days, and network issues can cause duplicate delivery. Without idempotency, a duplicate webhook would charge the customer twice or update order status incorrectly."

### 2. ✅ Correlation ID Middleware

**What:** Enables distributed tracing across services

**File:** `backend/src/common/middleware/correlation-id.middleware.ts`

**Integration:** Applied globally in `AppModule`

**How It Works:**
```typescript
// Every request gets unique UUID
Request arrives
  ↓
CorrelationIdMiddleware generates UUID: "abc-123-def-456"
  ↓
Attached to req.correlationId
  ↓
Returned in X-Correlation-ID header
  ↓
Logged in every operation
  ↓
Propagated to downstream services (AI service, databases)
```

**Production Scenario:**
```
User reports: "Payment failed at 2:30 PM"

Without correlation ID:
- Grep logs for timestamp → finds 1000+ requests
- Cannot identify which is the failing request
- Cannot trace across services (NestJS logs separate from FastAPI)

With correlation ID:
- Frontend displays error: "Payment failed [abc-123-def-456]"
- Search logs: correlationId:"abc-123-def-456"
- Results:
  [abc-123] 14:30:00 request_started POST /payments/checkout
  [abc-123] 14:30:00 stripe_session_created session_id=cs_test_...
  [abc-123] 14:30:05 stripe_webhook_received event_id=evt_...
  [abc-123] 14:30:05 webhook_signature_verification_failed
  [abc-123] 14:30:05 request_error status=400
- Root cause identified in seconds: Invalid webhook signature
```

**Interview Answer:**
> "We use correlation IDs for distributed tracing. Every request gets a unique UUID generated by middleware. This ID is attached to the request object, returned in response headers, and included in all logs. When debugging production issues, we can search logs by correlation ID to see the complete request flow across all services. For example, a payment request flows through: Frontend → Nginx → NestJS → Stripe → Webhook → Order update. All logs include the same correlation ID, making it trivial to trace the entire flow. This is essential for debugging distributed systems where requests span multiple services."

**Configuration:**
```typescript

  return this.authService.login(loginDto);
}
```

**Attack Prevention:**
```
Brute Force Attack Example:
- Attacker tries to guess admin password
- Attempt 1-5: Allowed (normal behavior)
- Attempt 6+: Blocked with 429 "Too many requests, retry in 15 minutes"
- Admin account protected
```

**Cost Savings:**
```
AI Abuse Scenario:
- Bot hits AI endpoint 10,000 times/hour
- Without rate limiting:
  10k × $0.002 (OpenAI cost) = $20/hour = $14,400/month
  
- With rate limiting (20 req/min per user):
  20 × 60 = 1,200 req/hour × $0.002 = $2.40/hour = $1,728/month
  
Savings: $12,672/month (87% cost reduction)
```

**Response Headers:**
```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 5
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1696950000
Retry-After: 900

{
  "statusCode": 429,
  "message": "Rate limit exceeded. Too many requests to POST:/auth/login. Try again in 900 seconds.",
  "error": "Too Many Requests",
  "retryAfter": 900
}
```

**Interview Answer:**
> "We implement rate limiting to prevent abuse and ensure fair resource sharing. For example, login is limited to 5 attempts per 15 minutes to prevent brute-force attacks. AI generation is limited to 20 requests per minute to prevent a single user from monopolizing expensive resources. We track limits per IP for anonymous users and per userId for authenticated users. Storage is MongoDB (could migrate to Redis at scale). Headers tell clients when they can retry. This prevents attacks and saves money—without rate limiting, a bot could cost us $14k/month in AI API fees. With rate limiting, that drops to ~$2k/month."

**After (Deep):**

```
Without indexes:
- 1000 concurrent users = 1000 queries/sec
- 500ms per query × 1000 = 500 seconds of work
- Server cannot handle load, crashes

With indexes:
- 5ms per query × 1000 = 5 seconds of work
- Server handles easily, users happy
```

**Verification:**
```javascript
// Check if index is used
db.products.find({ category: "audio" }).explain("executionStats")

// Good (using index):
{
  stage: "IXSCAN",
  indexName: "category_createdAt",
  executionTimeMillis: 5,
  totalDocsExamined: 50,
  nReturned: 50
}

// Bad (no index):
{
  stage: "COLLSCAN",  // ❌ Scanning all documents
  executionTimeMillis: 500,
  totalDocsExamined: 10000,  // Scanned everything
  nReturned: 50
}
```

**Interview Answer:**
> "We create indexes for all frequently-queried fields. For example, products are filtered by category and sorted by date, so we have a compound index on (category, createdAt). This changes the query from a collection scan (COLLSCAN) that examines all 10k documents in 500ms, to an index scan (IXSCAN) that examines 50 documents in 5ms—100x faster. The tradeoff is slower writes (each index adds overhead on INSERT/UPDATE) and storage cost (indexes require space). We balance this by only indexing fields used in queries. We also use sparse indexes where appropriate—for example, googleId is sparse because most users don't have Google auth, so we don't waste space indexing null values."

### 7. ✅ Graceful Shutdown

**What:** Complete in-flight requests before shutdown

**Integration:** `main.ts`

```typescript
// Enable graceful shutdown
app.enableShutdownHooks();
```

**How It Works:**
```
Deployment/restart initiated
  ↓
SIGTERM sent to process
  ↓
NestJS stops accepting new requests
  ↓
In-flight requests continue processing
  ↓
Cleanup: Close DB connections, flush logs
  ↓
Process exits (exit code 0)
```

**Without Graceful Shutdown:**
```
Request arrives at 14:30:00.000
  ↓
Deployment at 14:30:00.500
  ↓
Process killed immediately
  ↓
Request fails mid-processing
  ↓
User sees 502 Bad Gateway
  ↓
Order may be in inconsistent state
```

**With Graceful Shutdown:**
```
Request arrives at 14:30:00.000
  ↓
Deployment at 14:30:00.500
  ↓
Server stops accepting NEW requests
  ↓
Existing request completes at 14:30:00.800
  ↓
Process exits cleanly
  ↓
User receives 201 Created (success)
  ↓
Zero downtime
```

**Interview Answer:**
> "We enable graceful shutdown to prevent failed requests during deployments. When NestJS receives SIGTERM (shutdown signal), it stops accepting new requests but allows in-flight requests to complete. This prevents 502 errors and ensures data consistency. For example, a payment request that's halfway through processing won't be interrupted. We also set a grace period (default 10 seconds) to force shutdown if requests take too long. This is critical for zero-downtime deployments—users shouldn't experience errors just because we're deploying new code."

### 8. ✅ Request Lifecycle Documentation

**What:** Visual diagram of request flow through NestJS

**Documented in:** ADRs and inline comments

**Flow:**
```
HTTP Request (User's browser/API client)
  ↓
Nginx (Reverse proxy, TLS termination, compression)
  ↓
NestJS Application (Port 3000)
  ↓
CorrelationIdMiddleware (Generate/extract correlation ID)
  ↓
IdempotencyMiddleware (Check for duplicate requests)
  ↓
CORS Middleware (Validate origin)
  ↓
Body Parser (Parse JSON, preserve raw body for webhooks)
  ↓
Guards (JwtAuthGuard, RolesGuard, RateLimitGuard)
  ↓
Pipes (ValidationPipe: Validate DTO, transform types)
  ↓
Controller Method (Route handler)
  ↓
Service Method (Business logic)
  ↓
Repository/External Service (Data access, AI service, Stripe)
  ↓
Response Transformation (Interceptors)
  ↓
LoggingInterceptor (Log response with duration)
  ↓
Exception Filter (Handle errors, return standard format)
  ↓
HTTP Response (JSON back to client)
```

**Failure Points:**
```
Authentication fails → Guard throws UnauthorizedException → 401
Validation fails → Pipe throws BadRequestException → 400
Rate limit exceeded → Guard throws TooManyRequestsException → 429
Service error → Service throws InternalServerErrorException → 500
Database error → Exception filter catches → 500 with details
```

**Interview Answer:**
> "A request flows through several layers in NestJS. First, middleware runs in order: correlation ID generation, idempotency check, CORS validation. Then guards execute: authentication, authorization, rate limiting. If guards pass, pipes validate the request DTO. The controller delegates to services, which access databases or external APIs. Interceptors wrap the response, adding logging and transformation. If any layer throws an exception, exception filters catch it and return a consistent error format. This layered architecture separates concerns—middleware for cross-cutting concerns, guards for security, pipes for validation, services for business logic. Each layer has a single responsibility, making the system maintainable and testable."

### 9. ✅ Payment Webhook Idempotency (Integrated)

**What:** Stripe event deduplication in production

**Location:** `PaymentsService.handleStripeWebhook()`

**Problem:**
```
Stripe sends webhook: checkout.session.completed
  ↓
Backend processes: Mark order as PAID
  ↓
Network glitch: Response doesn't reach Stripe
  ↓
Stripe retries: Sends same webhook again
  ↓
WITHOUT IDEMPOTENCY: Order marked as PAID twice (?)
  ↓
RESULT: Duplicate notification, potential double-credit
```

**Solution:**
```typescript
async handleStripeWebhook(event: Stripe.Event) {
  // Use Stripe event ID as idempotency key
  const idempotencyKey = `stripe_webhook:${event.id}`;
  
  // Check if already processed
  if (await this.checkWebhookIdempotency(idempotencyKey)) {
    return { received: true }; // Duplicate, already handled
  }
  
  // Mark as processing (atomic, prevents race condition)
  await this.markWebhookAsProcessing(idempotencyKey);
  
  try {
    // Process webhook
    switch (event.type) {
      case 'checkout.session.completed':
        await this.syncOrderWithStripeSession(session);
        break;
      // ...
    }
    
    // Mark as successfully processed
    await this.markWebhookAsProcessed(idempotencyKey);
  } catch (error) {
    // Remove key so Stripe can retry
    await this.removeWebhookIdempotency(idempotencyKey);
    throw error;
  }
  
  return { received: true };
}
```

**Race Condition Handling:**
```
Two webhooks arrive simultaneously (failover scenario)
  ↓
Both try: markWebhookAsProcessing(key)
  ↓
MongoDB unique index on key
  ↓
First insert: Success
  ↓
Second insert: Duplicate key error (11000)
  ↓
Second request: Treated as duplicate, returns success
  ↓
Result: Webhook processed exactly once
```

**Interview Answer:**
> "Stripe webhooks can arrive multiple times due to network retries or failover. We prevent duplicate processing by using the Stripe event ID as an idempotency key. Before processing, we check if we've seen this event ID before. If yes, we return success immediately (idempotent). If no, we atomically mark it as processing using MongoDB's unique index—this prevents race conditions if two webhooks arrive simultaneously. After successful processing, we mark it as completed. If processing fails, we remove the key so Stripe can retry. This ensures each webhook is processed exactly once, preventing duplicate charges or incorrect order status updates."

### Staff-Level Question: "How do you prevent duplicate payment processing?"

- **HOW** they fail
- **WHEN** you'd change them

That's what separates Senior from Staff/Principal.
